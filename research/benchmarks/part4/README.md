# Light DEX benchmark pilot — Part 4 working notes

> These pilot numbers were measured before the 3 October 2026 append-only block journal and touched-account execution changes. They remain useful historical baselines, but are not current capacity limits. The newer 90-second capacity runs are stored locally under `benchmark_results/runs/` (ignored by Git); see each `summary.json` and `run.json` for the exact binary hash and validity checks.

For post-optimization, node-free exchange measurements across larger account sets, resting books, FIFO queues, and multiple fills, see the [4 October exchange-state scaling note](exchange_scaling_2026-10-04.md) and its [curated CSV](data/exchange_scaling_2026-10-04.csv).

This folder describes an opt-in, local benchmark, not a claim about production throughput. The headless runner uses the control plane's existing 13-participant fleet: three Binance-observing market makers, five random agents, and five local-book trend followers. It does **not** use fixed-seed synthetic agents or a matched replay. PBFT and HotStuff therefore see different live market data and different participant decisions; comparisons are observational pilot measurements, not controlled causal estimates.

## Reproduce

From the repository root, build the release binaries and run the commands in the [root README](../../../README.md#benchmarks). The pilot runs only when invoked directly. It launches isolated local clusters, records node JSON state under `benchmark_results/runs/`, and checks that all replicas are responsive and have the same persisted tip and exchange-state digest. Access to Binance's public BTCUSDT depth WebSocket is required; no Binance orders are sent.

The default matrix comprises 26 trials: node scaling at 4/7/13 replicas for both algorithms; timeout sweeps at 200/400/800/1500/3000 ms for seven replicas; additional mixed-order load targets of 15/40/80/160 TPS; and one repeat per algorithm. Each trial uses a 12-second warm-up and 30-second measurement by default. A guard stops starting further trials after 28 minutes. The completed runs below overrode both intervals to 20 seconds. Warm-up failures, stale market data, inconsistent or unresponsive replicas, and failed persisted-chain replay make the trial invalid; invalid points must not be used in throughput ratios.

`summary.json` holds trial-level numbers and `run.json` holds 500-ms samples plus source/binary provenance. `successful_tps` is the difference in a node's committed-success counter divided by measured wall time; `failed_tps` is committed execution failures. Their sum is included transactions/s; failed orders still consume block space. `submitted_writes` counts control-plane TCP sends, **not accepted or finalized transactions**. The extra offered TPS is a scheduler target, while `attempted_extra` is the actual attempted count. `latency_p50_ms` and `latency_p95_ms` are samples from node receipt to commit, not client round-trip latency. `max_backlog` is the largest sampled mempool, not a queueing estimate. Exchange microbenchmarks isolate state execution/digest cost on one process and must not be mixed with cluster TPS.

## Limits to keep visible in the article

- Binance depth and host load vary between trials. Run order is not randomized, and the pilot has only one or two observations per configuration.
- Transactions generated by agents are coupled to block inclusion and nonce availability. Increasing offered TPS may not increase accepted demand proportionally.
- The market's integer-dollar tick and the fleet's one-BTC quote size are simulator choices, not Binance execution conditions.
- A timeout setting that survived a short pilot is not a safety threshold. Longer trials, process-fault cases, and repeated runs are needed before making reliability claims.
- Full-chain replay and tip equality are end-of-trial correctness checks; they do not prove all submitted transactions were accepted or give a formal consensus-safety proof.

## Results from 2 October 2026

The unprofiled [26-trial pilot](data/pilot_summary.json) and the final [87-account load sweep](data/stress_summary.json) each passed their end-of-trial checks. The pilot and load sweep were run on an Intel Core i5-8365U laptop with 20-second warm-ups and 20-second measurement windows. The executable's SHA-256 and Git status are in each local `run.json`; the worktree was dirty, so a Git commit alone does not reproduce the binaries. An initial feed warm-up failure produced no valid comparison point. Two earlier load sweeps are retained in ignored raw results but superseded: one was scheduler-capped at 50 attempts/s, and the next used only 50 driver accounts.

### Consensus and node count

| Nodes | PBFT successful TPS | HotStuff successful TPS | PBFT p95 ms | HotStuff p95 ms |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 7.64 | 8.34 | 492 | 498 |
| 7 | 8.70 | 7.35 | 504 | 516 |
| 13 | 10.05 | 9.49 | 499 | 505 |

These are live-agent results, not an isolated consensus benchmark. Throughput did **not** monotonically fall as replicas increased; incoming market data and agent choices changed between runs. At seven nodes the repeat without extra load gave 7.04 TPS for PBFT and 6.60 for HotStuff, compared with 8.70 and 7.35 in the first run. That spread is a warning against claiming a precise algorithmic speed ratio. Sampled receipt-to-commit p95 clustered around the 500-ms block interval.

### Timeout floor, provisionally

Both algorithms passed all tested 200–3000 ms settings. However, at 200 ms the sum of per-node view advances was 42 for PBFT and 231 for HotStuff; at 400 ms it was 21 and 147. At 800 ms and above this count was zero in the tested 20-second runs. A reasonable *pilot operating point* is therefore about 800 ms or higher with the 500-ms block interval; 200–400 ms appears to create unnecessary view churn. This is not a proven failure threshold, and the short tests included no forced node faults.

### Mixed-order load on the 13-agent fleet

The extra driver uses 87 distinct funded genesis accounts, excluding the fleet's accounts 70–82, and permits one in-flight transaction per driver account. Its operation mix includes transfers, passive limit orders, crossing IOC/FOK orders, and cancels. The last point remains generator-limited at about 88 actual attempts/s.

| Extra target TPS | Actual extra attempts/s | PBFT successful / included TPS | HotStuff successful / included TPS | Max mempool, PBFT / HotStuff |
| ---: | ---: | ---: | ---: | ---: |
| 15 | 15 | 22.0 / 22.9 | 21.1 / 22.4 | 19 / 18 |
| 40 | 40 | 44.8 / 48.6 | 42.5 / 47.8 | 29 / 30 |
| 80 | 80 | 62.4 / 85.7 | 65.6 / 86.5 | 50 / 51 |
| 160 | 88 | 68.6 / 93.5 | 51.5 / 93.9 | 77 / 80 |

The 80-target trial shows clear queue pressure. At the highest target, the two algorithms included almost the same total number of transactions per second; the larger difference in *successful* TPS came from more execution failures in the HotStuff live run (mostly order behavior), not proof that HotStuff finalized fewer transactions. The rising backlog suggests the combined live workload approached or exceeded sustainable processing during these short windows, but 88 actual extra attempts/s and 20 seconds are insufficient to establish a hard capacity ceiling.

### Follow-up: bounded nonce pipeline, 3 October 2026

The benchmark driver now supports `--workload transfer --in-flight-per-account 4`. It assigns contiguous nonces per account, tracks every pending digest, retries a timed-out head, and submits a funded self-transfer at the **same nonce** if the head fails. It stops issuing new work for that account until the gap is repaired. Normal UI submissions still require the confirmed nonce; only the headless benchmark can submit future nonces, and the controller bounds that privilege to 32. Mixed, book-dependent orders remain at a window of one. At the end of measurement, the driver stops adding work and checks that its pending transactions drain before marking the trial valid.

The separate [pipelined-transfer summary](data/pipelined_transfer_summary.json) and [capacity figure](figures/pipelined_transfer/capacity_curve.svg) come from 7-node runs using the same 13-agent fleet, 15-second warm-ups, and 20-second measurements. These are **not** interchangeable with the mixed-order points above.
Successful TPS is the node's total for the live fleet plus extra transfers, not a count of transfer completions alone.

| Extra transfer target TPS | Actual extra attempts/s | PBFT successful TPS | HotStuff successful TPS | Pending at measurement end, PBFT / HotStuff |
| ---: | ---: | ---: | ---: | ---: |
| 80 | ~80 | 85.0 | 84.9 | 46 / 42 |
| 160 | ~160 | 162.3 | 162.5 | 91 / 88 |

All four transfer trials passed replica/replay checks and drained the pending benchmark transactions after measurement. Neither needed a nonce repair. The 160-TPS result shows that the earlier ~88 attempts/s ceiling was in the generator, not a demonstrated consensus limit. It does **not** establish sustained 160-TPS capacity: queued transactions at measurement end and mempool peaks near 90 call for longer steady-state runs.

The [mixed-order recheck](data/mixed_recheck_summary.json) and [figure](figures/mixed_recheck/capacity_curve.svg) kept a window of one. Those trials also passed and drained, but the 80/160 targets yielded roughly 72–79 new mixed-order attempts/s; 177–269 same-nonce repair submissions per trial were needed as FOK/cancel orders failed. Repair writes are counted separately from new attempted load. This distinction is why pipelined transfers are a cleaner consensus stress workload, while mixed orders remain useful for exchange behavior and failure-rate research.

### Exchange work and sampled CPU functions

The [isolated exchange microbench](data/exchange_microbench.csv) used 100 samples per operation and book fixtures of 0, 25, 100, and 250 resting orders. At 250 orders, p95 was about 0.030–0.044 ms for transfer, limit-order, IOC, and cancel execution, versus 0.092 ms for a full state digest. The transfer p95 rose from 0.013 ms at an empty book to 0.035 ms at 250 orders, consistent with the current `execute_with_receipt` cloning the full `ExchangeState` for each transaction. It is a small, cache-warm, one-process fixture—not a cluster latency measurement.

An [exchange-only `perf` sample](data/exchange-perf.txt) of 757 CPU samples put 22.2% of self samples in SHA-256 compression and substantial additional samples in allocator/free and collection clone paths. These percentages include fixture setup/cloning outside the microbench timer and cannot be assigned to a live node's total CPU budget. A lightly loaded node profile had only 12 samples, too few for a credible cluster-wide function ranking. Full-block persistence/replay and repeated logging of failed FOK/cancel transactions remain likely sources of load to instrument in a longer follow-up, but are not quantified here.

The article-ready [figures and source mapping](figures/summary.csv) were produced by `benchmarks/render.py`. The six SVGs show node scaling, timeout response, driver delivery/capacity/backlog, exchange costs, exchange-profile hotspots, and height/backlog over time. These curated files are tracked with the report; the detailed per-node traces and chain states remain local and ignored by Git.

## 3 October 2026 follow-up: 20 nodes, more participants, and storage/execution changes

All points below used HotStuff on the same i5-8365U laptop, a 25-second warm-up, a 90-second measurement, the live Binance-fed fleet, and the headless driver. There are 100 funded genesis accounts. A 30-participant run has 70 separate driver accounts; a 50-participant run has 50. `resting` submits one-BTC, non-crossing sell limit orders at high prices and **intentionally grows the book**; it is not a steady-state market. Successful TPS includes both driver and participant transactions. A clean capacity point delivered at least 95% of the offered extra rate, kept every node responsive throughout, drained pending driver transactions, and passed persisted replay and replica consistency checks. One run per point is not a confidence interval.

| Implementation | Nodes / participants | Extra workload | Target / delivered extra TPS | Total successful TPS | Outcome |
| --- | ---: | --- | ---: | ---: | --- |
| Before | 20 / 30 | Resting LO | 100 / 98 | 120 | Invalid: nodes exited or became unresponsive |
| After | 20 / 30 | Resting LO | 100 / 100 | 124 | Clean; 8,922 open orders |
| After | 20 / 30 | Resting LO | 200 / 200 | 223 | Clean; 17,931 open orders |
| After | 20 / 30 | Resting LO | 300 / 300 | 325 | Invalid: 5 nodes unresponsive near the end |
| Before | 20 / 30 | Transfer | 1000 / 999 | 1010 | Clean |
| After | 20 / 30 | Transfer | 1000 / 1000 | 1023 | Clean |
| After | 20 / 30 | Transfer | 1400 / 1398 | 1419 | Clean |
| After | 20 / 30 | Transfer | 1500 / 1404 | 1420 | Generator-limited; not a 1500-TPS capacity result |
| After | 7 / 30 | Transfer | 1000 / 1000 | 1018 | Clean |
| After | 20 / 50 | Resting LO | 50 / 50 | 104 | Clean; all 100 accounts active |

The matched 20-node 1000-TPS transfer runs used about **3.61 versus 2.11 aggregate node CPU cores** before/after, wrote **522 versus 7 MB per node** during measurement, and reported **1091 versus 552 ms** receipt-to-commit p95. This is a material performance change: older capacity curves must not be presented as current limits. With the optimized code, the seven-node matched point used 1.32 aggregate node CPU cores at roughly the same throughput and 538 ms p95; increasing to 20 nodes raised aggregate node CPU to 2.11 cores but did not materially lower throughput at this offered rate. For the 20-node, 200-order/s run, the controller itself used about 1.38 cores as full `NodeStatus` snapshots grew with the order book; status serialization/polling is now a likely operational limit. The 300-order/s run delivered load and kept committing, but failed the all-nodes-responsive condition, so the clean growing-book rate is bracketed between 200 and 300 extra orders/s in these 90-second tests. The transfer ceiling was **not** reached: 1400 extra TPS passed, while the 1500 target was not fully generated.

The isolated 250-order exchange microbenchmark's passive-LO p95 fell from 43.7 µs to 1.25 µs and transfer p95 from 35.0 µs to 0.54 µs; full-state digest p95 stayed near 0.09 ms. These are isolated operation timings, not cluster latencies. Raw `run.json` and `summary.json` files are local and ignored by Git; the key run directories are `pilot-1791055054077` and `pilot-1791056526423` before, and `pilot-1791057691197`, `pilot-1791057832651`, `pilot-1791058132986`, `pilot-1791058443103`, `pilot-1791058605345`, `pilot-1791058752717`, and `pilot-1791058985818` after the change. Each records binary hashes and sampled per-node counters.
